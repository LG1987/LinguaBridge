# 需求变更记录

记录对 [spec-v2.0-original.md](spec-v2.0-original.md) 的正式变更。编号规则：`RC-<三位序号>`。每条都写明「原方案怎么要求 → 变更后怎么要求 → 影响 → 实现约束 → 状态」。

---

## RC-001 · 发送即翻译（原文行为：只译草稿与回复）

- **提出时间**：2026-10-25
- **状态**：待实现（实现方式待定，见下）

### 变更内容

**原方案（v2.0）与 v0.1.0 的行为**

- 输入框里写中文 → 打开对比面板 → 用户确认后**写入英文** → 用户自己按发送；
- 会话里显示的是用户写入的内容；
- 助手回复译成中文，以独立卡片展示。

**变更后（RC-001）**

> 输入框里是中文，点击发送后，会话中**用户自己那条消息**（原截图红框位置）显示的是**英文译文**；模型收到的也是英文。

即：翻译发生在**发送动作**里，而不是发送之前的一次确认；用户消息的气泡本身就是英文。

### 影响

1. 与方案的"强制手动确认、绝不自动发送"底线冲突。RC-001 生效后，**发送即等价于确认**；是否保留一个可选的"发送前预览"需要产品决定。
2. 用户消息气泡的内容来源改变：必须让"翻译后的文本"而不是"输入的原文"进入会话记录（durable log），否则气泡仍显示中文。
3. 失败策略需要重新定义：翻译失败时是**拦截发送并提示**，还是**照发原文**？按项目既有原则（失败不发送、保留原文），倾向于拦截并提示。

### 实现约束（2026-10-25 实测）

| 能力 | 结论 | 依据 |
|------|------|------|
| 客户端"提交前"事件 | **不存在** | 客户端 Event 目录只有 `connection/reset`、`locale/change`、`slots/changed`、`theme/change` |
| 读写草稿 | 可行 | 插槽标准属性含 `useInput`（草稿快照）与 `inputActions`（实测含 `setDraft`、`submitDraft`、`persistDraft`） |
| 原生发送按钮的拦截 | **无公开钩子** | 提交动作由 composer 自身持有；`conversation.composer` 是 chain 插槽，接管等于整体替换 composer |
| 服务端侧改写「模型收到的消息」 | 可行但不满足要求 | host `agent/pre-step` 是 waterfall，可替换进入该 step 的 `messages`；但**气泡渲染自会话记录**，改写后气泡很可能仍是中文（待验证） |

### 可选实现方式

| 方案 | 用户动作 | 风险/成本 | 是否满足字面要求 |
|------|----------|-----------|------------------|
| **A. 独立「译并发送」按钮**（`conversation.input.right`） | 点一次这个按钮 | 低；不碰 composer | 结果为英文气泡 ✅；但按的不是原生发送键 ⚠️ |
| **B. 接管原生发送** | 点原生发送键 | 高；需替换 `conversation.composer` 或运行时改写 `inputActions`（脆弱，绑 DSH 版本） | ✅ 完全符合 |
| **C. 就地替换草稿**（点「译」→ 输入框变英文 → 自己发送） | 两次点击 | 最低 | 结果符合，但多一步 ⚠️ |
| **D. 仅 host 侧 `agent/pre-step` 改写** | 点原生发送键 | 中；不改变气泡显示 | ❌（模型收到英文，气泡仍是中文） |

### 待决问题

1. 选 A / B / C 中的哪一个（建议先 A，验证后再评估 B）。
2. 翻译失败时的行为：拦截发送并提示（建议）还是照发原文。
3. 是否保留"发送前预览"作为可选开关，默认关闭。

### 验收标准（草案）

- [ ] 输入框输入中文，触发发送动作后，会话中该条用户消息显示为英文
- [ ] 该条消息的英文与输入框原文语义一致，代码/路径/命令逐字保留
- [ ] 本地引擎不可达时，不发送、不清空草稿，并给出明确提示
- [ ] 关闭插件后，DSH 原生发送行为完全恢复
